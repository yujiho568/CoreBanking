# 2026-11-21 로컬 외부 조회 실험

환경: Windows, JDK 17, Gradle 8.13, Spring Boot 3.2.4. 각 조건은 워밍업 후 순차 요청
30건으로 측정했다. 작은 표본의 로컬 구성요소 실험이며 운영 처리량이나 금융결제원 성능을 나타내지 않는다.

## 로컬 HTTP 응답 재사용

실제 `KftcOpenBankingAdapter`가 loopback HTTP 서버를 호출한다. 서버에 30ms 지연을 주고,
같은 잔액 조회를 강제 갱신하는 경우와 이미 저장된 응답을 재사용하는 경우를 비교했다.
캐시는 `ConcurrentMapCache`다. Redis 왕복, 서비스의 소유권 DB 조회와 HTTP 컨트롤러 비용은 포함하지 않는다.

| 조건 | 평균 ms | p95 ms | 외부 HTTP 횟수 | 오류 |
|---|---:|---:|---:|---:|
| 매번 갱신 | 34.1835 | 35.0754 | 30 | 0 |
| 캐시 워밍업 후 재사용 | 0.0054 | 0.0009 | 0 | 0 |

캐시 조회 시간이 매우 작아 타이머·JIT 노이즈의 영향을 크게 받는다. 이 비율을 실제 Redis 도입 효과나
API 전체 응답시간 개선율로 사용하지 않는다. 확인한 핵심은 반복 조회에서 외부 호출을 생략한다는 점이다.
추가로 HTTP 500과 읽기 타임아웃을 재현해 예외 변환도 검증했다.

원시 측정값: [HTTP 실험 JSON](2026-11-21-external-http-benchmark.json).

## 반입 데이터 조회

실제 DATOP 원본은 사용하지 않았다. **원본 0건, 생성 30,000건**이며 계좌 참조값 300개에
100건씩 배분했다. 시간은 동일하게 두어 ID가 포함된 페이지 정렬도 사용한다.
H2 MySQL 모드와 `ConcurrentMapCache`에서 동일 서비스 쿼리를 측정했다.
소유권 확인을 위한 데이터셋 DB 조회 비용은 모든 조건에 포함한다.

| 조건 | 평균 ms | p95 ms | 오류 |
|---|---:|---:|---:|
| 복합 인덱스 제거, 매번 조회 | 6.2651 | 12.4840 | 0 |
| 복합 인덱스 적용, 매번 조회 | 5.4771 | 9.0144 | 0 |
| 캐시 워밍업 후 재사용 | 2.4273 | 4.5796 | 0 |

측정한 조건에서는 지연이 줄었지만 H2의 인덱스 동작을 MySQL의 실행 계획과 동일하게 해석하지 않는다.
실제 데이터 분포·건수로 MySQL `EXPLAIN ANALYZE`, Redis 사용 전후와 동시 HTTP 부하를 추가 측정해야 한다.

원시 측정값: [반입 조회 실험 JSON](2026-11-21-datop-query-benchmark.json).

## 테스트 결과와 미검증 범위

- 일반 Java 테스트: 26건 통과, MySQL 전용 통합 테스트 7건은 기존 실행 조건에 따라 건너뜀.
- 성능 실험 테스트: 2건 통과.
- CSV 정규화 Python 테스트: 1건 통과.
- 실행 JAR 빌드와 `git diff --check` 통과.
- Redis 저장 형식의 응답 직렬화 왕복은 테스트했다. 실제 Redis 서버의 TTL·네트워크 장애 동작은 미검증이다.
- Docker 데몬이 실행 중이 아니어서 실제 MySQL·Redis 조합의 통합 실험은 실행하지 못했다.
- 실제 금융결제원 인증·API 호출 및 실제 DATOP 데이터 반입은 실행하지 않았다.

재현 명령과 실제 서버 비교 도구는 [실행 안내](../external-query-performance.md)를 따른다.
